\section{Architecture}
\label{sec:architecture}
\label{sec:overview}
\label{sec:argument}

\Ziren{} proves one statement, the execution of a MIPS32 image (\S\ref{sec:statement}), and outputs a \emph{compressed proof} of it, which a \emph{native verifier} checks directly at the cost of the proof bytes it reads and its verification time. Figure~\ref{fig:architecture} draws the pipeline. Its core is two protocols, the shard argument (Protocol~\ref{prot:shard}) and the block argument (Protocol~\ref{prot:block}), symbolic in the public parameters the second lists. Terminal proofs then re-prove the compressed proof for verifiers with other costs or requirements (\S\ref{sec:applications}).

\centering

Two verification routes re-prove that proof (bottom): a shrink node re-proves it under the hash an application reads; the wrap closes it with a pairing-based SNARK for an on-chain verifier, and a binary stage over $\mathbb F_{2^{128}}$ and narrow recursion reach a garbled verifier.}
\label{fig:architecture}
\end{figure}

\paragraph{Execution.}\label{sec:arch-execution} The guest is executed once and the run is cut into shards, each described by the values its reads observe and its boundary registers. Every shard is then re-executed on its own to produce the event record its prover consumes, so shards are proved in parallel as they are produced and no party holds the record of the whole execution (\S\S\ref{sec:isa-record} and~\ref{sec:isa-emulator}). Nothing in the protocol depends on how the first pass is carried out.

\subsection{The shard argument}
\label{sec:arch-shard}
\label{sec:argument-components}
\label{sec:argument-shard}

Chips, with one row per executed instruction, and buses arithmetise a shard (Section~\ref{sec:air}). A bus argument $\mathsf{BA}$ (\LogUp{}, \S\ref{sec:air-logup}) and a constraint argument $\mathsf{CA}$ (a zerocheck, \S\ref{sec:air-zerocheck}) reduce every claim to column evaluations at one point; a jagged commitment $\mathsf{JC}$ reduces those to one evaluation of one dense polynomial (\S\ref{sec:pcs}), which one \WHIR{} opening authenticates (\S\ref{sec:iopp}). Each step ends with evaluation claims on committed columns, so the steps compose without the verifier reading a column.

\begin{protocol}[Shard argument]
\label{prot:shard}
\textbf{Statement:} a verifying key committing to the program and the
preprocessed tables, and the public values of one shard.\\
\textbf{Witness:} the shard's execution record.
\begin{enumerate}
  \item \textbf{Commit.} The prover arranges each chip's events into rows,
  places the columns of each commitment round into one dense vector and
  commits to it. Round order is fixed and the per-chip dimensions enter the
  transcript, so the geometry is public before any challenge is drawn
  (Section~\ref{sec:pcs}).
  \item \textbf{Buses.} The verifier draws the bus challenges. The prover runs
  the bus argument, which reduces every send and receive of every chip to
  column evaluations at one point (Section~\ref{sec:air-logup}).
  \item \textbf{Constraints.} The verifier draws the constraint challenges. The
  prover runs the constraint argument on the same point, so each column is
  opened once for both arguments (Section~\ref{sec:air-zerocheck}). In its
  univariate-skip form the first four rounds are one round over a sixteen-point
  domain, and the two steps below use the corresponding row weights
  (\S\S\ref{sec:air-skip} and~\ref{sec:pcs-skip}).
  \item \textbf{Jagged reduction.} The column claims of the two previous steps,
  together with explicit zero claims for the gaps in the committed geometry,
  are batched and reduced to one evaluation of the dense polynomial
  (Section~\ref{sec:pcs-jagged}).
  \item \textbf{Jagged assist.} The verifier does not materialise the indicator table
  the previous step reduced against: a second sumcheck over the public column
  boundaries certifies its evaluation, after which any point-extension coordinates
  are sampled (Section~\ref{sec:pcs-jagged-assist}).
  \item \textbf{Opening.} One batched opening authenticates that evaluation
  against every commitment of step~1 (Section~\ref{sec:iopp}).
\end{enumerate}
\textbf{Output:} a shard proof for the public values $\mathsf{pv}$ of
Definition~\ref{def:shard}.
\end{protocol}

\paragraph{Verifier checks.} The verifier absorbs the verifying key, the public values and the per-chip dimensions before drawing any challenge; checks every sumcheck round and closing identity of the bus argument, the constraint argument, the jagged sumcheck and the jagged assist, evaluating the constraint polynomials itself; checks Equation~\eqref{eq:stacking-bind}; runs the \WHIR{} verifier under the schedule; and checks that the public values are well formed. No quantity a soundness bound depends on is read from the proof beyond the declared heights, which the configuration caps (a column is at most $2^{22}$ rows, \S\ref{sec:pcs-geometry}): preprocessed row counts come from the verifying key and the schedule from the verifier's configuration. The recursive verifier checks every algebraic identity the native verifier checks.

\paragraph{Costs.} Let $A$ be a shard's committed area, $n_{\mathrm{int}}$ its number of bus interactions, $K$ its number of columns, $\rho$ the initial encoding rate and $L$ the largest Reed--Solomon encoding-domain size per stripe. For a fixed opening schedule, the prover performs $O(A + n_{\mathrm{int}})$ field operations outside the commitment, $O(A/\rho)$ hashing work and $O((A/\rho)\log L)$ field operations for FFT-based encoding. The verifier checks $O(\log^2 n_{\mathrm{int}})$ sumcheck rounds for the layered lookup circuit and $O(\log A)$ for each of the other three sumchecks, evaluates each chip's constraints once, spends $O(mK)$ on the jagged assist's closing identity (Theorem~\ref{thm:jagged-assist}), and checks the \WHIR{} queries, whose count is fixed by the schedule, as is the proof size (\S\ref{sec:perf-proofsize}).

\subsection{The block argument}
\label{sec:arch-recursion}
\label{sec:argument-block}

A recursion tree composes the shard proofs into one proof of the arithmetised relation $\mathcal R_{\mathrm{arith}}$ of \S\ref{sec:security-relation}, which \S\ref{sec:verification} connects to the relation $\mathcal R$ of \S\ref{sec:statement}. Leaves and compose nodes are recursion programs proved with the same shard argument; every node carries the public-value tuple of \S\ref{sec:security-binding}, and Algorithm~\ref{alg:compose} gives the checks on children and the root's additional conditions for closing the execution and the memory argument.

\begin{protocol}[Block proof, end to end]
\label{prot:block}
\textbf{Public parameters:} the field $\F$ and extension $\EF$, whose size bounds every term of the form $\deg/|\EF|$; the $\Poseidon{}$ transcript and Merkle trees; the \WHIR{} schedule and its decoding regime (Table~\ref{tab:whir-schedule}); the stacking height, row cube and bucket rule of the committed geometry (\S\ref{sec:pcs-geometry}); the compose arity (at most three) and the allowlist root $\mathsf{root}_K$ of the admissible leaf and compose keys; the machine's shard limits and guest-accelerator set, which fixes the chip set (\S\ref{sec:isa}); and the curve, interaction bound and multiplicity bound of the cross-shard digest (\S\ref{sec:air-digest-security}).

\smallskip
\noindent\textbf{Setup}$(P)$. Commit to the program ROM of image $P$ and to the preprocessed program, byte and range tables; output $(\mathsf{pk}, \mathsf{vk})$.

\smallskip
\noindent\textbf{Prove}$(\mathsf{pk}, P, \mathit{in}, \mathit{hint})$.
\begin{enumerate}
  \item \textbf{Execute and shard.} Execute $P$ on $(\mathit{in}, \mathit{hint})$ and cut the run into shards $T_0, \dots, T_{N-1}$ at the limits of \S\ref{sec:isa-record}, shard $T_i$ having index $i+1$ and the public values $\mathsf{pv}_i$ of Definition~\ref{def:shard}.
  \item \textbf{Prove the shards.} As each record is produced, prove it with the shard argument (Protocol~\ref{prot:shard}), giving $\pi_i$.
  \item \textbf{Leaves.} Quantise each shard's geometry into its class $\sigma_i = (\text{cluster}, \mathit{first}, b_{\mathrm p}, b_{\mathrm m}, \mathsf{pad}(b_{\mathrm m}))$. The leaf program of that class verifies $\pi_i$ against $\mathsf{vk}$ and outputs the compose tuple of the range; the first shard's leaf also requires $\mathsf{entry}_0 = \mathsf{start}(\mathsf{vk})$ and starting cursors of zero (\S\ref{sec:security-binding}).
  \item \textbf{Compose.} As soon as contiguous ranges are complete, merge up to three of them with a compose node, which performs the checks of Algorithm~\ref{alg:compose}.
  \item \textbf{Root.} Once one node covers $T_0, \dots, T_{N-1}$, a final compose node of arity one that verifies that node's proof, proved under the compress schedule, performs the root checks of Algorithm~\ref{alg:compose} and sets $\mathsf{complete}$. Its proof, with the recursion key $\mathsf{vk}^{\mathrm{rec}}$ that verifies it, is the compressed proof $\pi$.
\end{enumerate}

\noindent\textbf{Verify}$(\mathsf{vk}, h, \pi)$.
\begin{enumerate}
  \item Verify $\pi$ under $\mathsf{vk}^{\mathrm{rec}}$ with the shard verifier of \S\ref{sec:argument-shard} and the compress schedule, which the verifier fixes from the stage it expects and never reads from the proof.
  \item Require $\mathsf{vk}^{\mathrm{rec}}$ to be in the allowlist, the exported root to equal $\mathsf{root}_K$, and the completion flag to be set (\S\ref{sec:security-binding}).
  \item Require the exported guest key to equal $\mathsf{vk}$ and the exported output digest to equal $h$; accept.
\end{enumerate}
\end{protocol}

\paragraph{Admissible keys.} The allowlist contains 6\,494 leaf and compose keys determined by the declared chip clusters and committed shapes. The clusters are curated from target workloads rather than exhaustive over chip sets, so a shard outside them has no admissible key and is refused.

\paragraph{Pipelining.}\label{sec:perf-pipeline} Steps~2 to~4 of \textbf{Prove} overlap: a shard is proved as soon as its record exists and a compose node as soon as its children are proved. Only the root uses the schedule tuned for size (\S\ref{sec:perf-proofsize}). The start-up interval and the serial composes over the last shards remain (Table~\ref{tab:cards}).

\subsection{Terminal proofs and applications}
\label{sec:applications}

The compressed proof ends the proving stack for a native verifier. Three further proofs can follow it, each preserving the execution statement of $\pi$; Figure~\ref{fig:architecture} (bottom) shows the first and the third.

\paragraph{SNARK wrapping.} A shrink node re-proves the compressed proof, and a Groth16 or PLONK circuit over BN254 verifies the wrapped form while hashing in its native field. An \emph{on-chain verifier}, a contract that pays gas, checks the resulting proof with a constant number of pairings~\citep{groth16,plonk}. The inner proof is a private witness of that circuit, so a zero-knowledge instantiation hides it beyond what follows from the public execution statement. The circuit exposes the guest-key hash, the committed-values digest and the allowlist root; privacy is relative to these public inputs and to any application data published separately.

\paragraph{Zero-knowledge terminal proof.} Optionally, one hiding proof follows the recursion root, built from committed random rows, masked sumchecks and a hiding variant of the \WHIR{} opening (\S\ref{sec:zk}).

\paragraph{Garbled verification.} A \emph{garbled verifier} is a Boolean circuit evaluated under garbling~\citep{yao86}, as in protocols that check a computation on Bitcoin only when it is disputed~\citep{bitvm}: evaluating it on an invalid proof reveals a secret that serves as the fraud proof~\citep{glock}. Later protocols~\citep{bitvm3,argo-mac,babe,mosaic} garble the verifier of a pairing-based SNARK or of a designated-verifier variant of one; this route garbles a hash-based verifier. A garbled circuit pays for its AND gates and its input bits, while XOR gates are free~\citep{free-xor,half-gates}, so the route moves the arithmetic to $\mathbb F_{2^{128}}$, where an addition is a XOR, and the hash to \Blake{}~\citep{blake3}. A binary stage commits bit columns as packed elements of $\mathbb F_{2^{128}}$ and opens them through ring switching~\citep{binius,fri-binius}, emulating the shrink verifier's \KB{} arithmetic over bits. The run of its verifier is recorded as a tape of field operations, hash evaluations and comparison outcomes; a narrow machine over $\mathbb F_{2^{128}}$ proves a run of the tape, narrow recursion repeats the step on each narrow proof's own verifier, and the garbled circuit evaluates the last tape on the bits of the last narrow proof.

\paragraph{Applications.} A rollup can run its execution client as a MIPS32 guest and prove its state transitions. On Ethereum a verifier contract checks the wrapped execution proof as part of settlement; on Bitcoin the proof can be combined with a BitVM bridge and dispute protocol~\citep{bitvm2-implementation}, which determines how the proved state transition authorises a withdrawal or resolves a dispute. Private computation uses the hiding terminal proofs.
